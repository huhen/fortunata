## 1. Парсер `internal/timelottery`

### 1.1 Неоднозначная колонка с восемью числами

`numbersCell` вместо `([]int, bool)` возвращает `(nums []int, count int)`,
где `count` — сколько ячеек строки содержат ровно восемь чисел
(`count == 0` эквивалентен прежнему `false`). В `Parse`:

- `count == 1` — как раньше;
- `count > 1` — строка не разбирается «по первой», а уходит в
  `Issue{DrawNo, Reason: "неоднозначно: ячеек с восемью числами — N"}`;
- `count == 0` — не похоже на строку данных, пропускается.

Тест: фикстура со второй 8-числовой ячейкой в строке → issue с этой
причиной, розыгрыш не добавлен.

### 1.2 Прямые юнит-тесты `extractNumbers` / `validate`

Таблица кейсов для `extractNumbers`:

- «14 сент» → `[14]`, «93,3 млн» → `[93, 3]` (плотность колонок из спеки);
- юникод-разделители: «1–2» → `[1, 2]`, неразрывный пробел между числами;
- группа цифр в конце строки без терминатора: «7 и 11» → `[7, 11]`;
- переполнение: 19+ цифр — `Atoi` ошибается (ErrRange) и возвращает
  насыщенное `math.MaxInt` (`0` — только при ошибке синтаксиса). Текущее
  поведение фиксируется тестом как задокументированное; в реальной строке
  такой артефакт отсекается `validate` как issue (вне диапазона/повтор).

Для `validate`: валидная комбинация + каждая ветка отказа (число вне 1–35,
повтор, бонус вне 1–54).

### 1.3 `TestParseIssues` → подтесты

Кейсы переписываются на `t.Run` по номеру розыгрыша, после `found = true` —
`break`.

## 2. API `internal/api`

### 2.1 Тест ветки ошибки БД в `syncDraws`

`TestSyncStoreClosed`: собрать сервер и залогиниться (логин в БД не ходит),
затем `st.Close()` и `POST /api/sync` с валидным апстримом. Каждый
`Create` падает → ответ 200, `added == 0`, по issue «ошибка сохранения» на
каждый розыгрыш.

### 2.2 Тихая обрезка `io.LimitReader`

Вместо `io.LimitReader` — крошечный `limitedReader` (поле-счётчик остатка):
после исчерпания `maxArchiveBytes` возвращает сентинелл
`errArchiveTooBig` («страница архива больше 5 МБ»). `html.Parse` пробрасывает
ошибку ридера, `Parse` оборачивает через `%w`; `fetchArchive` распознаёт
`errors.Is(err, errArchiveTooBig)` и отдаёт чистый текст ошибки без префикса
«разбор html:» → 502.

Граничный случай принимается: страница размером ровно 5 МБ тоже отклоняется
(реальная ~0,2 МБ).

Тест: апстрим отдаёт `maxArchiveBytes + 1` байт → 502 с сообщением про
размер.

### 2.3 `archiveClient` → поле `Handler`

Package-level var убирается. В `api.go` минимальный рефакторинг:

- `newHandler(st, password, secret, cookieSecure, archiveURL) *Handler` —
  unexported конструктор, собирает `Handler` с полем
  `archiveClient *http.Client` (по умолчанию `&http.Client{Timeout: 10s}`);
- `(h *Handler) register(mux *http.ServeMux)` — вся регистрация маршрутов;
- `New(...)` = `newHandler` + `register`; сигнатура и поведение для `main`
  не меняются;
- `fetchArchive` становится методом `h.fetchArchive(url)`.

Тест таймаута: `newHandler(...)` напрямую, `h.archiveClient` подменяется на
клиент с `Timeout: 100ms`, апстрим спит 2 с → 502 «не удалось загрузить
страницу архива».

## 3. UI `web/admin.js`

### 3.1 Причина в итогах синхронизации

`syncSummary` показывает причину: `№ 62 (число 36 вне диапазона 1–35)`.
Для DB-ошибок читается как «№ 64 (ошибка сохранения)».

### 3.2 Защитная ветка «строка без номера»

Ветка сохраняется (решение: защитный контракт по спеке). Над `map` —
комментарий: парсер создаёт Issue только при № ≥ 1 и DB-ошибки всегда
с номером, ветка — защита от изменения парсера.

### 3.3 Live-region `#sync-status`

В `sync()` регион показывается (`hidden = false`) **до** записи текста —
смена текста в уже видимой `role="status"`-области объявляется скринридером
(канонический паттерн). `hidden = false` переезжает из `finally` в `try` и
`catch`; в начале синка прошлый итог по-прежнему скрывается.

## 5. Именование релизов (вне issue)

Сейчас `v$(дата коммита %Y.%m.%d)-$(хеш)` → два релиза за день отличаются
только хешем, лексическая сортировка не хронологична.

Новый формат: **`v2026.09.17-0834-6ff9686`** — `HHMM` от времени коммита
(без точки, фиксированная ширина с нулевым паддингом):

```
VERSION="v$(git show -s --format='%cd' --date=format:'%Y.%m.%d-%H%M' HEAD)-$(git rev-parse --short HEAD)"
```

- Источник времени — коммит, а не запуск workflow: версия остаётся
  детерминированной функцией коммита. Коллизия «два merge в одну минуту»
  практически исключена: релизы сериализованы (`concurrency: release-main`),
  сборка дольше минуты — теги разнесены по времени.
- Секунды не нужны (гранулярность минут достаточна при сериализованной
  очереди).
- Docker-тег `:v2026.09.17-0834-6ff9686` остаётся валидным.

Затрагивается: шаг «Версия» в `.github/workflows/release.yml` + спека
`2026-09-16-github-release-workflow-design.md` (два упоминания формата).
