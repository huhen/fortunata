# Дизайн: расписание автосинхронизации розыгрышей

Дата: 2026-10-28. Статус: согласован с пользователем.

## Проблема

Синхронизация архива (`POST /api/sync`) запускается только вручную из админки,
и пользователь про неё забывает. Нужен автоматический запуск раз в сутки,
по умолчанию в 15:00 UTC.

## Решения, принятые с пользователем

- Настройка — env-переменные `HH:MM` (без cron-библиотек).
- Догон при старте: если сегодняшние 15:00 UTC уже прошли — синка сразу.
- Ошибка синки — повтор каждый час до успеха; затем снова суточный ритм.
- Результат виден в админке (время, итог, ошибка, следующая автосинка).
- Статус хранится в памяти процесса, не в SQLite.

Отклонённые альтернативы: тикер в main.go (логика размазывается, не тестируется);
robfig/cron (библиотека ради одного суточного таймера).

## Архитектура

### Новый пакет `internal/scheduler`

Дженерик-планировщик «вызывай fn ежедневно в HH:MM UTC, при ошибке — повтор
через час». Ничего не знает о синхронизации.

```go
type Scheduler struct {
    hour, min int                    // время запуска в UTC
    fn        func(context.Context) error
    now       func() time.Time       // инъекция часов для тестов
    retryEvery time.Duration         // интервал повтора после ошибки (тестируется коротким)
}

func New(hour, min int, fn func(context.Context) error) *Scheduler
func (s *Scheduler) Run(ctx context.Context) // блокирующий цикл, запускается в горутине
```

Поведение цикла `Run`:

1. `nextRun(now, hour, min)` — ближайшие `HH:MM UTC` (сегодня, если ещё не
   наступили, иначе завтра). Если на момент старта сегодняшние `HH:MM` уже
   прошли — первый запуск немедленный (догон после рестарта; повтор безвреден,
   дубли пропускаются на уровне вставок).
2. Сон до `nextRun` через `time.Timer`, выбирающий и `ctx.Done()` (выход
   мгновенно — graceful shutdown).
3. Вызов `fn(ctx)`: успех → шаг 2 на завтра; ошибка → `slog.Warn` и повтор
   через `retryEvery` (по умолчанию 1 час), пока не получится.

`nextRun` — чистая функция, вынесена для табличных тестов.

### Извлечение логики синки (`internal/api`)

Из хендлера `syncDraws` вынимается метод:

```go
func (h *Handler) runSync(ctx context.Context) (syncResult, error)
```

— fetch → parse → вставки (существующая логика без изменений). Хендлер
`POST /api/sync` остаётся тонкой обёрткой: поведение и JSON-ответ не меняются.
`fetchArchive` получает ctx и делает запрос через
`http.NewRequestWithContext` (сейчас HTTP-запрос к архиву не отменяем).

### Статус последней синки

```go
type syncStatus struct {
    At      time.Time `json:"at"`
    Added   int       `json:"added"`
    Skipped int       `json:"skipped"`
    Issues  int       `json:"issues"`
    Err     string    `json:"error,omitempty"` // пусто = успех
}
```

Хранится в `Handler` как `lastSync *syncStatus` под `sync.Mutex`. Запись в
одной точке — обёртка `runSyncAndRecord(ctx) error`, которую вызывают:

- HTTP-хендлер `POST /api/sync` (ручная синка тоже обновляет статус);
- планировщик — `runSyncAndRecord` передаётся ему как `fn`, ошибка возвращается
  наружу для планирования повтора.

Ошибки отдельных вставок (попадают в `result.Issues`) — для планировщика
успех: страница получена и разобрана. Повтор нужен только при ошибке
fetch/parse. Гонка ручной и автоматической синки безвредна (идемпотентный
`Create`), лока не ставим.

### Эндпоинт `GET /api/sync-status`

Под `h.session`. Ответ:

```json
{
  "enabled": true,
  "schedule": "15:00 UTC",
  "nextRun": "2026-10-29T15:00:00Z",
  "last": {"at": "...", "added": 3, "skipped": 20, "issues": 0, "error": ""}
}
```

- `last` — `null` до первой синки после старта процесса (осознанно: догон при
  старте заполняет его сразу);
- `nextRun` — `null` при `enabled: false` и до первого расчёта планировщика;
  значение считает планировщик (метод `NextRun()` из закешированного
  следующего запуска).
- `schedule` — строка `"HH:MM UTC"` из конфига.

### Конфиг (`cmd/server/main.go`)

| Переменная | По умолчанию | Семантика |
|---|---|---|
| `SYNC_AT` | `15:00` | время суточной синки в UTC, формат `HH:MM`; невалидное значение — сервер не стартует |
| `SYNC_ENABLED` | `true` | `false` — планировщик не заводится, ручная синка работает |

`Config` получает поля `SyncAtHour, SyncAtMin int` и `SyncEnabled bool`.

Планировщик создаётся внутри `api.New` — иначе винегрет: его `fn` — метод
Handler, а Handler рождается в `api.New`. Сигнатура:

```go
type SyncConfig struct{ Hour, Min int; Enabled bool }
func New(..., llmClient *llm.Client, sync SyncConfig) (*http.ServeMux, *scheduler.Scheduler)
```

`api.New` после сборки Handler создаёт `scheduler.New(hour, min,
h.runSyncAndRecord)`, сохраняет его в Handler (для `GET /api/sync-status`) и
возвращает вторым значением; при `Enabled: false` возвращает `nil`-планировщик
(Handler помнит `enabled`/`schedule` для ответа статуса). `main` запускает
`go sched.Run(ctx)` на том же `ctx`, что и shutdown HTTP-сервера.
`Scheduler.NextRun()` считается на лету чистой функцией `nextRun`, поэтому
статус-эндпоинт корректен и до первого тика.

### UI (`web/admin.html`)

Под существующей кнопкой «Синхронизировать» — постоянная строка-подсказка,
заполняемая при загрузке админки запросом `GET /api/sync-status`:

> Автосинхронизация ежедневно в 15:00 UTC, следующая — 29 окт 15:00.
> Последняя: 28 окт 15:02, добавлено 3.

Варианты текста: `enabled: false` → «Автосинхронизация выключена»; `last:
null` → без второй фразы; `error` непустой → «ошибка: <текст>». Ручная синка
после завершения перезапрашивает статус. Существующий `#sync-status`
(мгновенный отклик ручной синки) не меняется.

## Тесты

- `internal/scheduler`: табличные тесты `nextRun` (до/после времени, граница
  суток); цикл `Run` с фейковыми часами (инъекция `now`, короткий
  `retryEvery`): старт до 15:00 → вызов в 15:00; старт после 15:00 → немедленный
  вызов; ошибка → повтор через retryEvery; успех после повтора → возврат к
  суточному ритму; отмена ctx → выход.
- `internal/api`: `runSyncAndRecord` пишет статус (успех, ошибка);
  `GET /api/sync-status` — 401 без сессии, JSON с сессией (включая `last:
  null`); существующие тесты `POST /api/sync` проходят без изменений.
- `cmd/server`: `loadConfig` — дефолты `SYNC_AT`/`SYNC_ENABLED`, парсинг
  валидных значений, ошибка на невалидных.

## Домены ошибок

- fetch/parse упал → статус с `error`, `slog.Warn`, повтор через час;
- частичные ошибки вставки → успех с `issues` в статусе;
- невалидный `SYNC_AT` → фатальная ошибка старта;
- рестарт в любой момент → догон при старте, статус пуст до первой синки.
