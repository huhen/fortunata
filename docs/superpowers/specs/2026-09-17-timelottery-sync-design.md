# Дизайн: синхронизация розыгрышей с архивом timelottery.ru

Дата: 2026-09-17
Статус: утверждён

## Цель

Кнопка «Синхронизировать» на странице «Редактирование розыгрышей»: сервер
скачивает страницу архива
<https://timelottery.ru/arhiv/rezultaty-vseh-rozygryshej-fortunata/>,
разбирает таблицу результатов и добавляет в базу только новые розыгрыши.
Существующие не трогаются. Пользователю выдаётся краткий итог (добавлено /
пропущено / ошибки).

## Решённые параметры

| Параметр | Значение |
|---|---|
| Где разбирается HTML | на сервере, пакет `internal/timelottery` (Go + `golang.org/x/net/html`) |
| Триггер | ручной: кнопка на админке → `POST /api/sync` |
| Мутация | только вставка новых; существующие розыгрыши не обновляются |
| Разбор страницы устойчив к смене дизайна | поиск строк по содержимому ячеек, без привязки к классам, стилям, порядку колонок и номеру таблицы (на странице три таблицы) |
| URL архива | константа в `internal/api`; в `api.New` добавляется параметр `archiveURL` (пустая строка → константа) для подстановки `httptest`-сервера в тестах |

## Пакет `internal/timelottery`

Чистая функция без сети и без доступа к БД:

```go
type Draw struct {
    No      int64 // номер розыгрыша
    Numbers []int // 7 основных чисел 1–35, по возрастанию
    Bonus   int   // бонусное число 1–54
}

type Issue struct {
    DrawNo int64  // 0, если номер строки не определился
    Reason string // человекочитаемая причина пропуска
}

// Parse разбирает HTML архива. Ошибка (третий возврат) — структурная:
// на странице не найдено ни одной строки с результатами.
func Parse(r io.Reader) ([]Draw, []Issue, error)
```

### Алгоритм и устойчивость к редизайну

1. Токенизация через `golang.org/x/net/html`; собираются все `<tr>`, для
   каждой строки — список текстов ячеек (`textContent` поддерева, теги
   `<strong>`/`<span>` учитывать не нужно — текст и так плоский).
2. Строка считается **строкой данных**, если:
   - первая ячейка целиком парсится как целое число ≥ 1 — это № розыгрыша;
   - среди остальных ячеек есть ячейка, где при разбиении текста на группы
     цифр получается **ровно 8 чисел** — это колонка «Выпавшие числа»
     (7 основных + бонус). Ячейки с восемью числами подсчитываются: если
     их больше одной — строка уходит в `Issue` (неоднозначность), парсер
     не угадывает.
3. Поиск по содержимому, а не по позиции: остальные колонки такой плотности
   цифр не дают (дата «14 сент» → 1 число, «10 млн» → 1, «93,3 млн» → 2,
   «архив (#64)» → 1). Колонки можно переставлять, добавлять и удалять —
   разбор не меняется. Таблицы, классы и inline-стили не участвуют вовсе,
   поэтому строки из двух других таблиц страницы отфильтровываются сами.
4. Разбиение на числа — по любым подстрокам без цифр (как в `web/parse.js`):
   переживает смену разделителей («, », « и », пробелы).
5. Валидация: первые 7 чисел в диапазоне 1–35 и не повторяются, восьмое в
   1–54. Провал → `Issue`, строка пропускается, разбор продолжается.
6. Молча (без `Issue`) пропускаются строки, которые не похожи на данные:
   первая ячейка — не целое число (шапка, сноски) либо среди ячеек нет ни
   одной с ровно 8 числами (например, строка соседней таблицы «Разыгранные
   джекпоты», начинающаяся с номера тиража). `Issue` — только для строк,
   *похожих* на данные, но с невалидной комбинацией (числа вне диапазона,
   повторы) или с неоднозначной колонкой (см. п. 2).
7. Если похожих на данные строк не найдено ни одной — структурная ошибка
   «на странице не найдены результаты розыгрышей». Системные изменения
   структуры сайта поэтому не портят данные тихо, а дают громкий отказ.

## Эндпоинт `POST /api/sync`

- Защита: `session` + `requireJSON`, как у остальных мутаций.
- `api.New` получает новый параметр `archiveURL string` (пустая строка →
  константа с реальным адресом); `http.Client{Timeout: 10s}` на уровне пакета
  (ревью: 10 с < WriteTimeout сервера 15 с, иначе вставки закоммитятся,
  а ответ до клиента не дойдёт).
- Поток: GET → проверка HTTP-статуса → чтение тела с лимитом 5 МБ →
  `timelottery.Parse` → вставка каждого розыгрыша через `store.Create`:
  - успех → «добавлен»;
  - `errors.Is(err, store.ErrDuplicate)` → «пропущен» (уже есть в базе; заодно
    покрывает дубли номеров внутри самой страницы);
  - прочая ошибка БД → уходит в `issues`, вставка продолжается.
- Ответ 200:

  ```json
  {"added": 2, "skipped": 61, "total": 64,
   "issues": [{"drawNo": 12, "reason": "…"}]}
  ```

  `total` — всего строк данных на странице: `added + skipped + len(issues)`
  (каждая строка данных попадает ровно в одну из трёх корзин: добавлена,
  уже была, или ушла в `issues` — от парсера или от ошибки БД).
- Ошибки апстрима — 502 с сообщением: «Не удалось загрузить страницу архива»
  (сеть, таймаут, не-200) или «На странице не найдены результаты розыгрышей»
  (структурная ошибка парсера).

## Фронтенд

- `admin.html`: в блоке form-actions рядом с «Добавить» кнопка
  `#btn-sync` (класс `btn-secondary`, текст «Синхронизировать») и
  `<p id="sync-status">` для результата.
- `admin.js`: по клику — кнопка дизейблится с текстом «Синхронизация…»,
  `POST /api/sync` (пустое тело `{}`), затем:
  - успех → в `sync-status`: «Добавлено N, пропущено M»; если были `Issue` —
    дополнение «не удалось разобрать: № 12, № 13» (номера с `DrawNo = 0`
    показываются как «строка без номера»); если N = 0 и issues нет —
    «Новых розыгрышей нет»;
  - ошибка API → текст из `error` красным в `sync-status`;
  - в конце — `refreshList()`, кнопка разблокируется.

## Тесты

- `internal/timelottery/timelottery_test.go`, фикстура — вырезка реального HTML
  страницы: шапка таблицы, несколько строк данных (включая № 64:
  «19, 28, 24, 21, 10, 29, 05 и 18»), строки соседних таблиц, битая строка.
  Кейсы:
  - разбор корректных строк (№ 64 → `{64, [10 19 21 24 28 29], 18}`);
  - битые строки → `Issue` с номером и причиной, остальные строки разобраны;
  - строка с двумя ячейками по 8 чисел (`testdata/ambiguous.html`,
    `TestParseAmbiguousRow`) → `Issue` (неоднозначно), а не розыгрыш;
  - HTML без строк данных → структурная ошибка;
  - строки другой таблицы и сноски не попадают в результат.
- `internal/api`: хендлер против `httptest`-сервера с фикстурой:
  - первый вызов: `added = N`, данные в базе совпадают;
  - второй вызов идемпотентен: `added = 0`, `skipped = N`;
  - апстрим отдаёт HTML без данных → 502;
  - без сессии → 401.

## Краевые случаи

- **Первый запуск, база пустая** — добавятся все ~64 розыгрыша одной кнопкой.
- **Розыгрыш есть в базе, но числа на сайте исправили** — не обновляется
  (осознанное требование), считается пропущенным.
- **Сайт недоступен / таймаут / редирект на капчу** — 502, кнопка показывает
  ошибку, база не меняется.
- **Сайт поменял структуру радикально** (нет строк с 8 числами) — 502 со
  структурным сообщением; частичные изменения структуры переживаются поиском
  по содержимому.
- **Дублирование номера на странице** — вторая вставка того же номера
  считается пропущенной (`ErrDuplicate`).

## Проверка

- `go test ./...` — новые тесты парсера и хендлера, старые зелёные.
- `go run ./cmd/server`, ручной прогон: вход → «Синхронизировать» → итог и
  обновлённый список; повторный клик → «Добавлено 0 …».
