# AI-генерация комбинаций через llama.cpp — дизайн

Дата: 2026-09-17
Статус: утверждён

## Задача

Кнопка «AI генерация» рядом с «Сгенерировать» на главной: LLM (llama.cpp-сервер
в домашней сети) предлагает N следующих комбинаций на основе правил лотереи,
статистики выпадений и количества прошедших тиражей. Результат отображается так
же, как у стандартной генерации. Некорректные комбинации из ответа LLM
отбрасываются и добираются повторным запросом.

## Решения

- Подход A: весь обмен с LLM — на бэкенде, новый пакет `internal/llm` с
  OpenAI-совместимым клиентом. Альтернативы отклонены: json_schema/грамматики
  llama.cpp привязали бы фичу к конкретному серверу и всё равно не спасли бы от
  дублей и чисел вне диапазона; запросы из браузера напрямую вскрыли бы
  api_key посетителям и потребовали CORS.
- Endpoint публичный, как `/api/generate` (на главной нет UI логина; сессия
  сломала бы UX). Каждый клик нагружает домашний LLM-сервер — осознанный
  компромисс для приватного деплоя.
- Количество — общее поле ввода, но для AI верхняя граница **20** вместо 100:
  длинные ответы LLM ломаются чаще, ретраи дорожают.
- Промт на английском (лучше качество у qwen3), ответ строго в JSON.
- Частичный результат допустим: после исчерпания доборов отдаём все валидные
  комбинации, даже если их меньше N (но ≥1). Ноль валидных — ошибка.

## Конфигурация

Новые переменные окружения (читаются в `loadConfig`, `cmd/server/main.go`):

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `LLM_BASE_URL` | База llama.cpp-сервера, напр. `http://192.168.1.128:18020`; клиент добавляет `/v1/chat/completions`. Пусто → фича выключена | *(пусто)* |
| `LLM_MODEL` | Имя модели, напр. `qwen3.8-27b` | *(пусто)* |
| `LLM_API_KEY` | Bearer-токен, опционален | *(пусто)* |

- Правило старта: `LLM_BASE_URL` и `LLM_MODEL` задаются вместе; только один из
  них — сервер не стартует с понятной ошибкой.
- `Config` получает три поля и передаётся в `api.New`.
- Для локальной проверки с реальным сервером значения кладутся в `.env`
  (в `.gitignore`); `go run` — после `set -a; source .env; set +a`, docker
  compose подхватывает `.env` сам.

## Бэкенд

### Endpoint

- Маршрут `POST /api/generate/ai` — публичный, `requireJSON`.
- Тело: `{"count": N}`, валидация `1..20` → иначе 400.
- Ответ 200: `{"tickets":[{"numbers":[7 чисел 1–35 по возрастанию],"bonus":1–54}]}`
  — тот же формат, что у `/api/generate`; фронт переиспользует рендер.

### Пакет `internal/llm`

```go
type Client struct { /* baseURL, model, apiKey, hc *http.Client */ }
```

- `hc` подменяемый — тесты через `httptest` (паттерн `archiveClient` в
  `internal/api/api.go`).
- Один вызов: `POST {baseURL}/v1/chat/completions`,
  `messages: [{system}, {user}]`, `temperature: 0.8`, `max_tokens: 4096`
  (запас на `<think>`-рассуждения qwen3 и 20 комбинаций); ответ —
  `choices[0].message.content`.
- Таймаут клиента: константа 120 с.

### Промт (EN)

- **System**: роль «lottery combination proposer»; правила — 7 distinct numbers
  1–35 ascending + 1 bonus number 1–54; формат ответа — только JSON-объект
  `{"combinations":[{"numbers":[...],"bonus":n}]}`, без markdown, пояснений и
  текста вокруг.
- **User**: просьба предложить N комбинаций; количество прошедших тиражей;
  частота выпадения каждого основного шара 1–35 и бонусного 1–54 (число:
  количество). При доборе — список уже найденных комбинаций с запретом
  повторять их.

### Парсинг и валидация

- Срезаются `<think>...</think>`-блоки (qwen3 думает по умолчанию) и
  ```-заборы; JSON-объект ищется в тексте устойчиво к окружающему мусору.
- Каждый кандидат: ровно 7 чисел, уникальные, 1–35, сортируются; бонус 1–54.
  Невалидные отбрасываются.
- Дубли внутри пачки отбрасываются (ключ = отсортированные числа + бонус).

### Добор (ретраи)

Взяли валидные → если их меньше N и доборы не исчерпаны (максимум **2**),
повторный запрос на `N − len(валидных)` комбинаций с exclude-списком. После
исчерпания отдаём что набрали (см. «Решения»). Добор применяется только к
невалидному/непарсируемому **контенту**; сетевые ошибки и не-200 от LLM не
ретраятся — сразу ошибка пользователю. Неспарсируемый ответ целиком считается
нулом валидных комбинаций и уходит в добор.

### Ошибки API

| Ситуация | Ответ |
|---|---|
| `LLM_BASE_URL` пуст | 503 «AI генерация не настроена» |
| Сетевой сбой / таймаут до LLM | 502 «LLM-сервер недоступен» |
| LLM вернул не-200 | 502 с HTTP-кодом в тексте |
| После доборов ноль валидных | 502 «LLM не смог предложить корректные комбинации» |
| Валидных меньше N, но ≥1 | 200, отдаём сколько есть; факт недобора — в slog |

### Хендлер

`List()` из стора → `generate.Frequencies` (переиспользуется) → промт → вызов
`internal/llm` → парс/валидация → доборы → ответ. Ошибка БД → 500 как в
`/api/generate`.

### Таймауты сервера

`WriteTimeout` HTTP-сервера в `cmd/server/main.go`: 15 с → **130 с** — иначе
ответ LLM умрёт при записи (комментарий в коде). `ReadTimeout`,
`IdleTimeout`, таймаут `archiveClient` не меняются.

## Фронтенд

### `web/index.html`

Кнопка `<button id="btn-generate-ai" class="btn-primary" hidden>AI генерация</button>`
рядом с `#btn-generate` в той же карточке.

### `web/app.js`

- `GET /api/version` дополняется полем `ai: bool` (LLM сконфигурирован).
  `app.js` при загрузке запрашивает `/api/version` и показывает кнопку только
  при `ai: true` — публичный деплой без `LLM_*` не показывает мёртвую кнопку.
- Клики: тот же `count` из `#count`; во время запроса кнопка disabled с
  текстом «AI думает…», `#count` тоже disabled (ответ может идти ~2 минуты).
- Результат — в существующий `#tickets`, шары через `ball()`; ошибки — в
  существующий `#gen-error`. Клиентская валидация count не дублируется: если в
  поле >20, сервер вернёт 400, и сообщение покажется в `#gen-error`.

## Docker и документация

- `compose.yaml`: passthrough `LLM_BASE_URL`/`LLM_MODEL`/`LLM_API_KEY` с пустыми
  дефолтами (`${LLM_BASE_URL:-}`).
- `compose.local.yaml`: значения пользователя (URL, модель), `LLM_API_KEY` через
  `${LLM_API_KEY:-}` из `.env`.
- `.env.example`: закомментированный блок с пояснениями.
- README: таблица переменных дополняется; CLAUDE.md: строка про `internal/llm`
  в «Архитектуре».

## Тесты

- `internal/llm`: парсер — чистый JSON, ответ с `<think>`, с ```-заборами, с
  текстовым мусором вокруг; валидатор — вне диапазона, дубли, несортированный
  ввод; `ComposePrompt` содержит N, статистику, правила и exclude-список.
- `internal/api` (httptest-заглушка LLM): happy path; добор при невалидных;
  ноль валидных → 502; upstream 500 → 502; не настроено → 503; `count` 21 →
  400; endpoint доступен без сессии.
- `cmd/server`: `loadConfig` читает `LLM_*`; ошибка старта при задании только
  одного из пары.
- JS-тесты не пишутся: парсинг целиком на бэкенде, инфраструктура JS-тестов
  есть только у `parse.js`.

## Граничные случаи

- Пустой архив (0 тиражей): фича всё равно работает — промт получает нулевые
  частоты и «0 past draws»; LLM предлагает комбинации без опоры на статистику.
- LLM вернул больше N комбинаций: берём первые N валидных.
- Пользователь без cookie нажал AI-кнопку: работает, авторизации нет.

## Не входит в объём

- Стриминг ответа LLM (SSE) — ожидание с кнопкой-спиннером достаточно.
- Выбор модели/параметров из UI.
- Кэширование ответов LLM.
- Constrained decoding (json_schema/GBNF) — можно добавить позже как улучшение
  к существующей валидации.
